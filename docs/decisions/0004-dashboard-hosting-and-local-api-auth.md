# ADR-0004 Dashboard 托管方式与本地 API 鉴权

| 项 | 内容 |
| --- | --- |
| 状态 | 已接受（M0 验证项 S5，2026-11-14） |
| 日期 | 2026-11-14 |

## 背景

Dashboard 是网页，Bridge 在本机提供 API。需要回答两个问题：网页从哪里加载；怎样保证只有用户自己打开的 Dashboard 能控制硬件。

只绑定回环地址并不够。用户浏览的任何网页都能向 `http://127.0.0.1:端口` 发请求，因此存在三类威胁：

| 威胁 | 说明 |
| --- | --- |
| 跨站请求 | 恶意网页直接请求本地 API 来读取设备信息或修改设置 |
| DNS 重绑定 | 恶意域名解析到 127.0.0.1，使请求在浏览器看来是同源的，从而绕过跨域限制 |
| 设备指纹 | 恶意网页通过只读接口获知用户拥有哪些外设 |

同一用户下的其他本地进程不在防护范围内，它们本来就能直接访问 HID（SEC-07）。

## 决定

### 1. Dashboard 由 Bridge 同源提供

Bridge 内嵌一份固定版本的 Dashboard 构建产物，在 `http://127.0.0.1:<端口>/` 提供。

- 离线可用（WEB-01、需求场景 E）。
- Dashboard 与 Bridge 版本始终匹配。
- 白名单里只有 Bridge 自己这一个源。

### 2. 会话通过托盘发起的一次性握手建立

1. 用户在托盘菜单点“打开 Dashboard”。
2. Bridge 生成一次性授权码，用默认浏览器打开 `/auth?code=…`。
3. Bridge 校验授权码，下发会话 Cookie（`HttpOnly`、`SameSite=Strict`），重定向到 `/`。
4. 授权码单次有效、短时过期。会话在 Bridge 退出时失效。

直接在浏览器输入地址而没有会话时，页面只显示“请从托盘打开”的说明，不暴露任何设备信息。

同源场景用 Cookie 而不是在脚本里保存令牌：事件流连接不便自定义请求头，`HttpOnly` Cookie 也不会被页面脚本读取。

### 3. 每个请求的校验

| 校验 | 作用 |
| --- | --- |
| Host 头必须是 `127.0.0.1:<端口>` 或 `localhost:<端口>` | 抵御 DNS 重绑定 |
| 会话有效 | 所有接口都要求，包括只读接口，避免设备指纹 |
| 带 Origin 的请求，其值必须在白名单内 | 抵御跨站请求；事件流的升级请求同样检查 |
| 不设置宽松的跨域响应头 | 默认拒绝跨源读取 |

### 4. 不提供原始 HID 透传

本地 API 只有能力级操作。即使会话被冒用，攻击者能做的也仅限驱动已声明的能力，发不出任意报文（SEC-04）。

### 5. 端口

默认端口暂定 27463，被占用时顺延，并把实际端口写入用户级运行时文件。同源方案下由托盘打开正确地址，端口变化对用户不可见。

同一台机器上多个用户同时登录时各有一个 Bridge 实例，端口必然不同，这一点在设计托管版时要考虑。

## 托管版 Dashboard（P1，不在本次决定范围内）

将来提供在线托管版时：

- 托管页面的源必须经用户在 Bridge 侧显式确认后才加入白名单（SEC-03）。
- 跨源场景改用配对后下发的令牌。
- 浏览器对公网页面访问回环地址的限制在持续收紧，届时须按当时的浏览器行为重新评估可行性。

## 备选方案

| 方案 | 未采用的原因 |
| --- | --- |
| 只提供在线托管版，Bridge 维护来源白名单（OpenMouse 的做法） | 断网时无法打开界面；需要长期运营一个站点；受上述浏览器限制影响 |
| 原生界面替代网页 | 没有本地 HTTP 攻击面，但偏离“统一网页控制台”的产品形态，且界面要按平台重做 |
| 把 Dashboard 包进内嵌浏览器窗口 | 可作为将来的可选外壳；首期增加体积，且与 PERF-03 冲突 |
| 仅靠 Origin 白名单，不设会话 | 非浏览器客户端可伪造 Origin；只读接口仍可能被用来做设备指纹 |

## M0 验证结果

原型：axum 0.8 服务，监听 `127.0.0.1:27463`，内嵌一个静态页面、一个设备列表接口和一个服务器推送事件流。

| # | 请求 | 期望 | 结果 |
| --- | --- | --- | --- |
| 1 | 无会话访问 `/` | 只显示“请从托盘进入” | 通过 |
| 2 | 无会话访问 API | 401 | 通过 |
| 3 | 错误的授权码 | 401 | 通过 |
| 4 | 正确的授权码 | 303 跳转到 `/`，下发 `HttpOnly`、`SameSite=Strict` 会话 Cookie | 通过 |
| 5 | 重复使用同一授权码 | 401 | 通过 |
| 6 | 有会话访问 API | 200 | 通过 |
| 7 | 有会话、Host 头为外部域名（DNS 重绑定） | 403 | 通过 |
| 8 | 有会话、Origin 为外部站点 | 403 | 通过 |
| 9 | 有会话、Origin 为 Bridge 自身 | 200 | 通过 |
| 10 | 伪造的会话 Cookie | 401 | 通过 |
| 11 | 外部站点的跨域预检 | 403，无跨域响应头 | 通过 |
| 12 | 有会话订阅事件流 | 持续收到事件 | 通过 |
| 13 | 无会话订阅事件流 | 401 | 通过 |
| 14 | Edge：由程序用默认浏览器打开授权地址 | 进入 Dashboard，事件流工作 | 通过 |
| 15 | Edge：会话期间手动输入地址 | 直接进入 Dashboard | 通过 |

第 1 至 13 项用 curl 测试，第 14、15 项由项目发起人在 Edge 中确认。其他浏览器未测。

## 后果

- 首次使用必须经托盘进入 Dashboard，不能收藏地址后直接打开。会话存续期间可以直接访问。
- Bridge 的发布包含 Dashboard，`waishe` 仓库的每次 Dashboard 发布需要 Bridge 跟进一次版本。
- 需要实现并测试 Host、Origin、会话三项校验，对应验收条件 AC-12。
