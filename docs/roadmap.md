## M0 技术验证

目的：在写正式代码之前，验证或推翻需求第 9 节中的假设。产出是结论和数据，代码可以丢弃。

| 验证项 | 要回答的问题 | 通过标准 |
| --- | --- | --- |
| S1 设备可达性 | 不安装厂商软件、无管理员权限，能否在 Windows 上读到 DeathAdder V3 Pro 的电量、DPI、回报率，以及 Cloud III Wireless 的电量、充电、静音状态？有线与 2.4G 分别如何？ | 两款设备的全部 P0 能力各至少成功读取一次；DPI 与回报率各成功写入并回读一次 |
| S2 厂商软件共存 | Synapse 或 NGENUITY 运行时，读取是否仍然可靠？写入是否被覆盖？ | 得出明确结论并写入设备文档；确定 CFG-04 的提示文案依据 |
| S3 插件运行时 | 候选运行时（见 ADR-0003）的体积、内存、调用延迟是多少？驱动能否在沙箱内完成 S1 的一次电量读取和一次事件监听？ | 有实测数据；满足 ADR-0003 列出的门槛，或触发其退路 |
| S4 托盘与通知 | Rust 下托盘图标、动态电量图标、系统通知、用户级自启在 Windows 10/11 上是否可行？ | 四项各有可运行的最小示例 |
| S5 同源 Dashboard 与鉴权 | 由 Bridge 提供静态页面、托盘发起一次性握手、令牌校验、Host/Origin 校验的流程是否顺畅？ | 流程走通；无令牌和跨源请求被拒绝 |
| S6 设备归并 | Windows 上把多个 HID 接口归并为一个端点的依据是否可靠？ | 两款设备各只归并出一个端点 |

**进展**

| 验证项 | 状态 | 结论 |
| --- | --- | --- |
| S1 | 通过（2026-11-14） | 两款设备的全部 P0 能力在无管理员权限、无厂商软件时可读；DeathAdder V3 Pro 的 DPI 与回报率可写入并回读。DeathAdder 有线模式未测 |
| S2 | 部分完成 | 厂商软件运行时读写均正常，10 秒内未被覆盖；输入报告广播给所有句柄。长时间共存未测 |
| S3 | 未开始 | 需要 Rust 工具链 |
| S4 | 未开始 | 需要 Rust 工具链 |
| S5 | 未开始 | 需要 Rust 工具链 |
| S6 | 通过（2026-11-14） | 以容器 ID 归并，两个接收器各归并为一个端点 |

详细记录：`driver-razer` 仓库 `docs/deathadder-v3-pro.md`，`driver-hyperx` 仓库 `docs/cloud-iii-wireless.md`。

**退出条件**

- S1 通过。S1 不通过则回到需求阶段重新评估首批设备。
- ADR-0003、ADR-0004 由“提案”改为“已接受”或被替代。
- 需求第 10 节的 Q3、Q4、Q7、Q8、Q10 有结论。
- 性能指标 PERF-01 至 PERF-05 用实测数据修订。

**顺序**：S1 最先做，它决定项目是否成立。S3 依赖 S1 得到的协议知识。S4、S5、S6 可与 S3 并行。

## M1 双设备闭环

目的：满足首期验收条件 AC-01 至 AC-13，驱动通过本地旁加载安装。

| 仓库 | 交付 |
| --- | --- |
| `waishe-driver-sdk` | 驱动接口 0.1、能力模型 0.1、驱动侧库、回放测试工具 |
| `waishe-bridge` | 设备发现与归并、驱动宿主、端点操作队列、调度器、状态存储、本地 API 0.1、托盘与通知、自启、安装包 |
| `waishe` | Dashboard：设备列表、能力驱动的详情页、驱动管理（本地安装/卸载/禁用）、设置；中英文 |
| `driver-razer` | DeathAdder V3 Pro：电量、DPI、回报率、连接状态、充电状态（协议支持时） |
| `driver-hyperx` | Cloud III Wireless：电量、充电、连接状态、静音状态 |

**退出条件**：AC-01 至 AC-13 全部通过，并有记录。所有里程碑列为 M1 的 P0 需求完成。

## M2 Registry 与在线安装

目的：完成“发现设备 → 提示 → 安装驱动”的完整流程，发布首个公开版本。

| 仓库 | 交付 |
| --- | --- |
| `waishe-driver-registry` | 索引格式 1.0、签名流程、收录流程与自动检查、两款首批驱动的条目 |
| `waishe-bridge` | Registry 客户端、内置索引快照、驱动在线安装/更新/回滚、Bridge 更新检查 |
| `waishe` | 未安装驱动设备的提示、驱动更新界面、验证等级展示 |
| `.github` | 贡献流程、设备支持请求流程实际运转 |

**退出条件**

- 全新安装的 Bridge，在没有任何驱动的状态下，通过界面完成两款设备的驱动安装并达到 M1 的验收状态。
- 人为发布一个探测必然失败的驱动版本，更新后自动回滚。
- 断网时已安装驱动的功能不受影响。
- 所有 P0 需求完成。发布 0.1.0。

## M3 增强与第三款设备

目的：验证扩展性，交付 P1 功能。

- 第三款设备优先选不同品牌、最好由社区贡献者在独立仓库完成，用来检验 SDK 与收录流程是否真的不需要改动 Bridge 和 Dashboard。
- P1 功能：DPI 档位、板载配置、配置档、独立托盘图标、按设备阈值、软件静音控制、音量、键盘电量、设备别名、诊断包、托管版 Dashboard。
- 驱动接口 1.0 冻结。

**退出条件**：第三款设备的驱动在不修改 Bridge 与 Dashboard 源码的前提下上线；驱动接口 1.0 发布。

## M4 蓝牙与 Linux

- 蓝牙设备电量（BLE Battery Service、经典蓝牙）。
- Linux 版 Bridge：hidraw 权限规则、托盘、自启、打包。
- macOS 视社区需求决定。
