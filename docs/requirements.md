## 1. 背景与问题

外设配置与状态查看目前依赖各厂商独立软件（Razer Synapse、Logitech G HUB、HyperX NGENUITY、SteelSeries GG 等）。同时使用多个品牌时：

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | 管理分散 | 每个品牌一个入口 |
| 2 | 基础功能重复 | 电量、DPI、回报率在每家软件中各实现一遍 |
| 3 | 资源占用 | 为少量基础功能常驻完整厂商套件 |
| 4 | 设备类型割裂 | 现有开源方案各管一类：鼠标配置、耳机电量、RGB |
| 5 | 扩展性不足 | 私有协议各异，缺少社区可扩展的统一驱动体系 |
| 6 | 纯网页驱动受限 | 浏览器权限、接口保护、无法后台运行。例：OpenMouse 说明 Chrome 153 起 Razer 控制接口受保护，需经本地 Bridge 访问 |

OpenMouse、BatteryMonitor、HyperBatteryMonitor 等项目各自解决了其中一部分，见[参考项目](references.md)。

## 2. 产品定位

**WaiShe 是一个轻量、本地优先、可扩展的跨品牌外设统一管理平台：一个本地常驻程序 + 一个统一网页控制台 + 按需安装的设备驱动。**

核心价值是统一用户最常用、各厂商重复实现的基础管理能力，而不是复刻任何一家厂商软件的全部功能。

### 2.1 目标

- G1 一个入口发现并管理不同品牌、不同类型的外设。
- G2 不打开网页也能在系统托盘看到所有外设的电量。
- G3 只安装自己设备需要的驱动；新增设备不需要重装 WaiShe。
- G4 日常使用不依赖厂商软件常驻，也不依赖网络。
- G5 第三方可在独立仓库开发驱动并经 Registry 分发。

### 2.2 非目标

见[第 8 节](#8-首期不纳入)。

### 2.3 设计原则与可检验含义

| 原则 | 可检验含义 |
| --- | --- |
| 统一性 | 同一能力在任何品牌的设备上使用同一个界面控件和同一种 API 形状 |
| 轻量化 | 安装包不含任何品牌的协议实现；没有对应设备在线的驱动不加载 |
| 模块化 | 新增一个品牌的支持不需要修改 Bridge 或 Dashboard 源码（新增能力类型除外） |
| 本地优先 | 断网时已安装驱动的全部功能可用；任何设备操作都不经过云端 |
| 可扩展性 | 仅依赖 SDK 和公开规范即可在独立仓库完成一个驱动 |
| 开放性 | 接口规范、兼容列表、验证记录全部公开 |
| 可靠性 | 每个值都带来源和时效；失败返回明确错误，不用默认值掩盖 |
| 最小权限（新增） | 网页拿不到原始 HID 通道；驱动拿不到匹配规则之外的设备 |

## 3. 产品组成

| 组成 | 仓库 | 职责 | 明确不负责 |
| --- | --- | --- | --- |
| Web Dashboard | `waishe` | 展示设备与状态、按能力渲染配置界面、驱动管理、偏好设置 | 硬件通信、协议知识 |
| Bridge | `waishe-bridge` | 设备发现、驱动宿主、HID 访问仲裁、状态缓存、后台监控、托盘与通知、原生设置面板、本地 API、提供 Dashboard 静态资源 | 品牌协议实现 |

| Driver SDK | `waishe-driver-sdk` | 驱动接口规范、能力模型、开发与测试工具 | — |
| Driver Registry | `waishe-driver-registry` | 设备兼容表、驱动索引、版本与下载信息、验证记录 | 操作用户硬件、收集用户数据 |

## 4. 概念模型与术语

初稿中“设备”一词同时指 USB 设备、接收器和用户手里的外设。以下定义用于消除歧义，后续所有需求均按此理解。

| 术语 | 定义 |
| --- | --- |
| 设备（Device） | 用户眼中的一个外设，例如一只鼠标。Dashboard 和托盘的展示单位 |
| 端点（Endpoint） | 设备的一条连接路径：有线 USB、2.4G 接收器或蓝牙。一个设备可同时有多个端点（接收器在线的同时插线充电） |
| 接收器（Receiver） | 承载 2.4G 端点的 USB 设备。接收器在线不等于设备在线 |
| 接口 / 集合 | 一个 USB 设备暴露的 HID 接口及顶层集合。Windows 为每个顶层集合生成独立设备路径 |
| 能力（Capability） | 标准化的功能单元，如 `battery.level`、`mouse.dpi`。界面与 API 的最小单位 |
| 驱动（Driver） | 按品牌或协议族组织的用户态协议适配器，以驱动包形式分发 |
| 设备表 | 驱动内的数据表：型号、VID/PID、连接方式、能力及其验证等级 |
| 验证等级 | `verified` 实机验证 / `simulated` 回放测试通过 / `inferred` 同协议族推断 / `broken` 已知不可用 |
| 信任层级 | `official` 官方驱动 / `community` 社区驱动且被 Registry 收录 / `local` 本地旁加载 |

### 4.1 值的四种状态

任何能力读数必须是以下之一，禁止用 0、100 或其他默认值代替：

| 状态 | 含义 | 界面表现 |
| --- | --- | --- |
| `ok` | 读取成功，附读取时间 | 显示值 |
| `unsupported` | 该设备或当前连接方式没有此能力 | 隐藏或禁用控件 |
| `unavailable` | 有此能力但现在读不到，附原因：休眠、断连、设备忙、通信错误 | 显示“暂时不可用”及原因 |
| `unknown` | 尚未读取过 | 显示“未知” |

另有 **历史值** 标记：最近一次 `ok` 的值超过时效阈值，或设备已断连。历史值可以保留展示，但必须在界面与托盘上与实时值视觉区分，并显示读取时间。

### 4.2 写入的四种结果

| 结果 | 含义 |
| --- | --- |
| `applied` | 已写入并经回读确认 |
| `accepted` | 设备确认收到，但协议无法回读 |
| `rejected` | 参数非法或设备不支持，未发送或被设备拒绝 |
| `failed` | 通信错误或超时，设备实际状态不确定，需重新读取 |

界面以结果为准，不做乐观更新。

## 6. 非功能需求

### 6.1 性能与资源（PERF）

全部为暂定指标，M0 结束时用实测数据修订。

| ID | 指标 |
| --- | --- |
| PERF-01 | 无 Dashboard 连接、两个设备在线时：平均 CPU 低于单核 0.1%，私有内存低于 40 MB |
| PERF-02 | 无设备在线时不加载任何驱动，没有周期性硬件访问 |
| PERF-03 | 安装包小于 20 MB |
| PERF-04 | 冷启动到托盘显示首个电量读数小于 5 秒 |
| PERF-05 | 设备在线时，一次 DPI 写入从点击到返回结果小于 500 毫秒 |

指标修订：PERF-01 的内存口径由“常驻内存”改为“私有内存”。工作集包含与其他进程共享的系统库页面，受托盘菜单等系统组件影响很大，M0 实测同一进程在打开托盘菜单前后工作集从 20.8 MiB 跳到 35.6 MiB，而私有内存为 2.6 MiB 到 9.5 MiB。

M0 分项实测（尚无集成后的 Bridge，以下仅作参照）：

| 组件原型 | 可执行文件 | 私有内存 | 其他 |
| --- | --- | --- | --- |
| 托盘、通知、电量读取（S4） | 0.7 MB | 2.6 MiB；打开托盘菜单后 9.5 MiB | 每 10 秒读取两台设备时约占单核 0.16% |
| 驱动运行时 + 两个驱动（S3，wasmi） | 2.5 MB | 加载后增加 2.1 MiB | 单个驱动加载 0.3–0.4 ms |
| 本地 API 与静态页面（S5） | 1.3 MB | 未测 | — |

DPI 写入并回读在 S1 中实测 124–165 ms（PERF-05 要求 500 ms 以内）。

### 6.2 稳定性（REL）

| ID | 需求 |
| --- | --- |
| REL-01 | 单个驱动异常不导致 Bridge 退出（同 DRV-05） |
| REL-02 | 插拔、睡眠唤醒后状态正确（同 DISC-02、DISC-03） |
| REL-03 | 所有硬件调用有超时；错误分类明确：超时、设备忙、无权限、协议错误、设备休眠 |
| REL-04 | 驱动安装与更新是原子操作，中途失败可恢复 |
| REL-05 | 不影响设备正常输入与音频：不读取、不独占系统输入集合的输入报告，不打开音频接口。控制报文位于系统输入集合上时，以访问权限 0 打开并只收发特性报告 |
| REL-06 | 不向设备发送固件升级、引导加载程序类命令 |

### 6.3 安全（SEC）

| ID | 需求 |
| --- | --- |
| SEC-01 | 本地 API 只监听回环地址，并校验 Host 头以抵御 DNS 重绑定 |
| SEC-02 | 全部 API（含只读）需要会话令牌；令牌通过由托盘发起的一次性握手取得 |
| SEC-03 | Origin 白名单默认只包含 Bridge 自身；托管版 Dashboard 的源必须经用户显式配对 |
| SEC-04 | 网页只能调用能力级 API，Bridge 不向网页提供原始 HID 透传 |
| SEC-05 | 驱动在沙箱中运行（同 DRV-06） |
| SEC-06 | 驱动包须通过签名与哈希校验；未受信任的驱动不自动执行 |
| SEC-07 | 威胁模型边界：同一用户下的其他本地进程不在防护范围内，它们本就能直接访问 HID |

鉴权设计见 [ADR-0004](decisions/0004-dashboard-hosting-and-local-api-auth.md)。

### 6.4 隐私（PRIV）

| ID | 需求 |

| PRIV-01 | 不需要账号 |
| PRIV-02 | 首发不含遥测；将来若加入，必须明确告知并由用户选择开启 |
| PRIV-03 | 设备序列号与 HID 报文不离开本机 |

## 11. 相对初稿的变更

**新增**

- 概念模型：设备 / 端点 / 接收器的区分（第 4 节），解决“同一接收器、多个 HID 接口”的去重问题。
- 值的四种状态与历史值标记（4.1），把“不用默认值代替”变成可实现的规则。
- 写入的四种结果（4.2），把“不能点了保存就算成功”变成可实现的规则。
- 驱动必须支持设备主动上报（HEAD-04），否则无法读取麦克风静音状态。
- 写入持久性声明（MOUSE-05）与重新枚举处理（MOUSE-06）。
- 厂商软件共存策略（CFG-04）。
- 本地 API 鉴权的具体要求（SEC-01 至 SEC-04、SEC-07），包括不提供原始 HID 透传。
- 隐私保护的本地匹配（PRIV-04）：不向 Registry 上报设备清单。
- 本地旁加载与开发者模式（DRV-03），使首期验收不依赖 Registry 上线。
- Bridge 应用自身的需求（5.10）与 Dashboard 通用需求（5.9）。
- 可度量的首期验收条件（7.2），含断连、睡眠唤醒、故障注入、离线、鉴权等反向用例。
- 风险与假设（第 9 节）、待决事项（第 10 节）。
- 设计原则“最小权限”。

**调整**

- 需求分两步交付：M1 用本地旁加载完成双设备闭环，M2 再交付 Registry 在线安装。初稿的九步安装流程对应 DRV-10。
- Dashboard 首发由 Bridge 本地提供；在线托管版降为 P1。理由：离线场景与鉴权简单性，见 ADR-0004。
- 蓝牙从“后续扩展”明确为 M4，不纳入首期。
- 性能指标从“原型后确定”改为给出暂定值，便于 M0 有对照目标。

**未改变**

产品定位、四个组成部分、首批两款设备、优先级划分、多仓库组织方式、技术方向倾向（Rust、WASM 作为候选）。
